Worktree `/home/oscar/Work/ox-multi-host`, branch `feat/multi-host`, based on `f44befe`. Oscar and the implementer will review the tradeoffs together before opening a PR.

## Decisions for review

- A host's UUID lives in a private, atomically created `host-id` file. An older host can rewrite its own ledger without dropping the UUID. Renaming the machine or restarting OX preserves its identity. Purging the state creates a new identity. Older hello frames can omit the UUID.
- The QR code and pasted invitation keep the existing long secret. The manual code uses twelve case-insensitive base32 characters, displayed in groups of four. Typing twelve characters costs more than a six-digit PIN. I think that cost is worth it for a credential that can enroll a device able to approve commands. All three forms spend the same single-use invitation and require the invitee's Tailscale login.
- Headless pairing and desktop Settings use the same Serve checks, listener reservation and confirmation. A public Funnel or another application's mapping on port 8443 stops pairing. I think requiring the owner to fix that mapping is worth the friction because a new device can control sessions.
- Device class is stored at registration. The authenticated bridge supplies the surface to the host on each connection. Existing registrations default to phone. Local argv handoffs and the remote terminal grant are distinct permissions.

- A desktop can explicitly copy selected provider and Brave Search keys to a paired host. The review names the target, scopes, possible charges, and continued use after revocation. Replacing existing keys requires selecting them. Copies retain their provider endpoint and the host's environment takes precedence.
- Managed headless installations default to automatic updates at idle. The operator can switch to download-only or manual and select Dev or Stable. An active turn, pending approval or active remote terminal delays installation. I think this wait is worth preserving live work.
- Wave 1 used Claude Opus 5.5 via OX on the subscription. Its findings prompted the separate host ID file, an older-host pairing error and prefix/label revocation. One invitation can still enroll either operator device. A host-to-host link grants different capabilities and needs separate enrollment. The read-only worker's approval prompt for returning findings is tracked in [#26](https://github.com/oxstack/ox/issues/26).

## Wave 7 · Host mode policy

- The operator can choose Follow interface, Always read, Always write, Always auto-review, Always YOLO or YOLO asks every time. Follow interface is the default for existing installations. A desktop can set the policy while adding a host or from Settings → Hosts. The paired web UI has the same control under Settings → Remote access. On the host, `ox host policy` shows the current setting and `ox host policy set always-write` changes it. The setting applies to every paired operator.
- A fixed policy controls starting permissions and maps to the native runtime. A lower draft or worker request is honored. The operator can change an open session. A worker's launch stamp distinguishes the starting mode from the authority the caller gave it. Worker resumes also honor the narrower starting contract. Reopening a live view preserves its current mode. The host writes policy changes atomically.
- YOLO asks every time holds the action that would actually use YOLO. Accept, lower and decline work across devices. A new-session request keeps the original text, images, route and sender until an operator answers it. The submitting device receives a successful send acknowledgement only after acceptance. A declined request replays its refusal. Draft approvals appear in the fleet inbox and phone catalog and have their own expiring push reference. A saved Codex transcript can be viewed silently. The first attempted turn in its restored YOLO mode waits for approval.
- **Tradeoff to discuss before the PR.** On a host explicitly set to YOLO asks every time, an existing grant or a client flag cannot answer for the operator. Starting or switching into YOLO takes one live approval, including after a real process resume. This makes the setting mean the same thing on a phone, desktop and agent request. Choosing a mode in a draft, reading history or reconnecting to the same running session needs no additional confirmation. Always YOLO and Follow interface remain available. Stock sessions controlled directly in an external terminal are outside this OX setting.

## Wave 8 · Git checkout transfer for remote workers

- The source captures the current tracked working tree into a temporary Git object store and index. Staged additions, working edits, recreated staged deletions, sparse and split indexes, linked worktrees, unborn branches and SHA-256 repositories have Linux fixtures. The source keeps its own index, stash and refs. A receiver that already has the base gets an incremental Git bundle. A warm, unchanged checkout needs no bundle.
- A target can seed its mirror from a registered local checkout, then refresh using its own origin. An unavailable origin leaves its cache usable. Each job owns its Git directory, excludes, branch and objects. The worker can continue after mirror pruning. Interrupted or rejected transfers leave no visible job. Populated submodules carry their own working snapshots and private inputs. A submodule URL from a transferred checkout is never contacted during launch.
- Binary content and private inputs stream through host disk. A real Git LFS 3.8.1 test transferred a modified binary offline, checked its bytes on the worker, and verified that a subsequent Git add retained its pointer. The target uses its own installed clean filter. Each repository has a private manifest recording the bytes and modes of transferred inputs so result delivery can identify edits or deletions.
- **Guardrail to discuss before the PR.** I would stop a launch if Git cannot keep a transferred input out of an ordinary `git add -A`. Two verified cases are a newline in its filename and a higher-priority tracked `.gitignore` rule that explicitly includes it. This costs the operator a rename or ignore-rule edit in those cases. It preserves the plan’s promise for a worker that later pushes to the origin. Ordinary transfers have no new confirmation or size limit. Shallow sources and submodules transfer even to an empty target. A target that already has fuller history keeps it. A partial clone missing promised objects reports how to complete the transfer.
- The transfer currently runs through the host-service library and real Git fixtures. Authenticated worker-link pairing, live launch and resume, remote notices, result publication and result cleanup still need their respective paths. Result publication must account for force-added private inputs throughout the outgoing history and for submodule commits that exist only on the target. Those results need a private delivery path. A transfer itself performs no push.

## Wave 12 · Deliver the parent’s checkout to a linked host

- A host with a worker link can send a Git snapshot over its signed connection. The receiving host selects one of its own registered checkouts by Git origin. Both hosts negotiate existing commits before streaming the missing objects, tracked edits and private untracked inputs. This is the transport that the cross-host worker launcher will use.
- The receiver verifies the archive length, checksum and snapshot commit, then publishes the isolated checkout and its receipt together. A retry with the same request recovers that receipt, even when two deliveries race. A different request cannot replace an existing job. Revocation stops an unfinished transfer. Startup removes abandoned staging directories and keeps published work.
- The isolated two-host TLS test exercises simultaneous sends, a lost-reply retry, an absent repository, and a grant disabled before and during upload. The target reuses a 2 MiB common base, receives the staged-then-edited file and the private untracked input, and omits the ignored file. Git status, refs and staged changes in both original checkouts survive unchanged. The mirror test also advances the receiving clone with its upstream offline and protects newer upstream tips from a stale clone.
- **Decision for the PR discussion.** I would keep the receiver’s check for a matching registered repository. That costs one initial `ox host project add DIR` on a fresh headless machine and prevents a parent from choosing an arbitrary filesystem destination. OX checks available disk space and whether the link is alive. Large repositories and long-running Git operations have no fixed transfer budget. Disabling new launches preserves already installed checkouts so that running work and recoverable results survive.

## Wave 14 · Choose a worker host by hardware, label or project rule

A project rule can send tracked and non-ignored untracked input to the chosen host. An explicit **Same as parent** overrides the rule. ## Wave 18 · Return a write worker’s changes

- A writable linked job uses the destination saved with its launch. Project settings override individual user defaults. - **Decision for the PR discussion.** Keep the default useful for CI. Publishing a branch includes the tracked parent edits and local commits it descends from. Only staged or committed new files belong in that publication. Other non-ignored new files remain available in the private return checkout. This costs a deliberate `git add` when a worker wants a new file in CI. It keeps incidental files out of a shared repository. Force-adding a transferred private path, even in an intermediate commit, selects private delivery for that result.
- **Decision for the PR discussion.** A refused push falls back immediately and records the reason. The same applies when the target cannot verify a new LFS pointer or submodule dependency. OX leaves an existing different result ref alone. Retirement uses the original push destination fingerprint and an expected-commit lease. The target retires the origin ref after archival or its configured age. A merged result can be released by the parent once its original source branch contains the commit. The default age is 30 days. The parent retains the separate working copy so its private files remain recoverable. Continuing a completed worker on its target starts an operator turn in that checkout.
