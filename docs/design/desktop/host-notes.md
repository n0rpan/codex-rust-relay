# OX session host

The desktop application and the phone web app subscribe to the same per-user session host. The host owns each native runtime, its controls and its pending approvals. Closing a client tears down that client's subscription. New local sessions start the host on demand. `ox host install` enables it for future logins using systemd user services on Linux or launchd on macOS. `ox host status` reports its state. `ox host uninstall` removes the login service.

## Local boundary

The native protocol uses newline-delimited JSON on a Unix socket in a private, user-owned directory. Both sides negotiate version 1. The daemon checks the peer's OS user. A canonical project directory and billing route identify a store. Codex retains a separate app-server for each such boundary. Claude maintains a process per native session. Native clients continue to own login, provider credentials and transcript files. Metadata discovery reads unopened native histories without beginning a turn. An unavailable or unverifiable saved billing route cannot silently become a different route.

Clients receive a catalog of projects and routes and the actions available on their selected session. Both interfaces subscribe to a live navigation catalog across projects. Its snapshot and deltas carry session rows, activity, parent IDs and pending-request indicators. Opening a session subscribes to its project and route for transcript and approval detail. The desktop falls back to the earlier all-scope subscription when connected to an older host. The initial snapshot includes session identities and parentage, ordered timeline items, capabilities and pending asks. A transcript item is keyed by thread, turn and item ID. Content updates replace the indicated item or append text to it. A session can change model, permissions or available actions during a turn. Clients use the host's confirmed capabilities for controls.

The phone and desktop session lists draw the same seven-by-seven source icons. Subscription threads use the Codex or Claude icon, API threads use the diamond, and nested sessions and workers use the worker icon. The separate status label shows running work and pending requests. The Chromium fixture checks the four silhouettes and compares idle and running sessions on both API routes.

Each broadcast has a cursor comprising a boot epoch and a sequence number. Sequence numbers apply to the host, so a scoped subscriber can see gaps. Reconnecting with a retained cursor receives subsequent matching deltas. A stale cursor or another boot epoch yields a fresh authoritative snapshot. Clients replace local projections on snapshots. Slow peers have a bounded outbound queue and may reconnect. The in-memory replay window retains at most 4,096 broadcasts or 8 MiB. Native stdout readers, socket writers and GPUI painting run independently.

Each action includes a correlation ID, scope and explicit native action. An approval additionally requires an opaque token for the pending request on that live connection. The host serializes decisions. The first valid answer reaches the runtime. Subsequent answers observe resolution or receive an error. Clients never resubmit a tool decision to recover a lost connection. The host checks the caller’s subscription before looking up a receipt. An action ID belongs to its canonical project, route and native runtime incarnation. Within the 2,048 most recent receipts, a retry with identical content returns the recorded result. If that request created a thread, the retry also returns its verified ID. A changed request under the same ID receives an error. Opening a terminal is a one-time handoff to the requesting client.

The wire types live in `desktop/ox-desk-core/src/host_protocol.rs`. Run `cargo run --locked --manifest-path desktop/Cargo.toml -p ox-host-protocol -- --check` to check the generated JSON Schema and TypeScript declarations.

## Recovery

The small per-user ledger records owned session identities, project and route, parentage, outstanding approval identities and a reserved sequence watermark. Atomic replacement and directory synchronization protect a completed write. The replay ring is memory-only. A new host epoch retires outstanding asks and reports previously active work as interrupted. Reopening a saved session reads its native transcript and revalidates its identity and route before new work. A host restart never replays a previous approval, prompt, worker launch or handoff. A pending YOLO request is retired on a new host epoch and reported to its parent as declined. A handoff interrupted before the target's first turn is reported as failed on the source and never retried; a handoff target that started is an ordinary session. Worker origin stamps, the final worker answer, and pending parent notices survive in the ledger. Native transcripts stay in the runtime’s own history. A private per-boot lifetime socket ties native OX process groups to their owner, including unexpected host death. Losing a launching OX helper closes its descendants’ group leases. A replacement runtime revalidates retained native thread identities and clears the previous transcript projections before restoring native history.

## Upgrade, restart and diagnostics

A new host version takes over by draining the old one. `ox host restart` (which `install.sh --desktop` runs when a host is running) sends the running host SIGUSR1. The host then refuses new turns, workers and handoffs, from clients and from agents, with a reason that says it is restarting for an update. Running turns continue and their approvals and questions stay answerable. When no turn is running, or the bound passes (600 seconds by default, `--timeout` to change it), the host records `last-stop.json` (reason, version, the number of turns still running) and exits. The restart command then starts the installed host through the login service, or detached. The new host has a new epoch, so the usual recovery rules apply: clients get a fresh snapshot, unfinished turns are reported interrupted, and pending YOLO requests and unstarted handoffs are retired, never replayed. Their reasons say "restarted for an update from <version>" when the previous host drained, "was stopped and started again" after SIGTERM, and "restarted" after a crash. A host from before drain support has no version in its hello; restart stops it with SIGTERM and says its running turns were interrupted.

The hello carries the host's build version and boot epoch. When the client's and host's protocol versions differ, both sides name the side to update: an older host is fixed with `ox host restart`, an older client by rerunning the installer or reloading the phone page.

`ox host stop` stops the host at once. `ox host uninstall` removes only the login service. `ox host uninstall --purge` also deletes the host state directory (ledger, pairings, push keys) after checking it holds the host's startup lock; Codex and Claude Code homes are never touched. On macOS, an account without a GUI session gets its launchd agent in the `user/<uid>` domain.

`ox host doctor` prints one line per check and exits non-zero on a blocking problem: host version, epoch, pid, protocol and capabilities; the login service; the last stop; paired devices and their last contact; remote access against `tailscale serve status --json` (blocking if Serve is off, routes elsewhere or Funnel is on); Codex and Claude Code versions against the floors in `desktop/gate.toml` (blocking below the floor or when neither is installed); the project and route of each saved scope; and the last host errors. The host appends its errors to `host-errors.log` in its state directory, rotated at 64 KiB. Lines hold error strings only, never prompts, commands or tool arguments.

## Worker ownership and permissions

An OX worker is an ordinary native Codex or Claude Code session that the host owns. It runs in its own project and billing route, beside other sessions on that route, with the shared transcript, asks, badges and Web Push. Operators open, steer, stop, approve, answer, continue, fork, rename, archive and hand it to `/terminal` with the usual session actions, as the runtime's capabilities allow.

When a host is running, the gateway's `start_ox_worker` asks the host to launch the worker. A helper the host started uses its private lifetime endpoint. Any other helper, such as `ox claude` in a terminal, connects to the per-user host socket as a same-user peer. The request carries the launch identity, route, mode, task, model and requested access. The host checks policy before opening any runtime, then opens or reuses the worker route, applies the starting permission mode and sends the task. The gateway's reply arrives once the native session exists. A worker does not belong to the launching helper's lifetime group, so losing the parent's process leaves the worker running. Host recovery, epochs and lease rules apply to workers as to other sessions.

The host resolves every gateway request to exactly one caller before it does anything, and launches, listings, status, steering and cancellation all use that one result. For a hosted helper the caller is a session with an active turn on that helper's project and route. A Claude helper serves one session and names it. A Codex app-server multiplexes threads, so the gateway forwards the calling thread from the stock client's MCP request metadata: Codex 0.171.0 and later put `_meta.threadId` on every `tools/call` (`with_mcp_tool_call_ids_meta` in `codex-rs/core/src/mcp_tool_call.rs`), and `desktop/tests/codex_thread_meta.py` checks each release in the protocol job. The host accepts that thread only if it is an active session on that route. A worker on its parent's app-server is therefore its own caller and cannot see or control its siblings, and its own children nest under it. Without a thread ID, the host accepts only a route with a single active session and refuses every parent operation otherwise. An MCP tool argument never chooses the parent.

A terminal helper's parent is its launch. The launch holds a random token that only it and the host see; stamps and catalog rows carry a digest of it. The launch also names its native session whenever it can, and every worker it starts records that session in its stamp. A Codex launch takes the calling thread from `_meta.threadId`, which arrives with the `start_ox_worker` call itself, or from `ox codex resume <id>`. Stock Claude Code sends no session identity to MCP servers (`desktop/tests/claude_mcp_meta.py` checks each track), so OX fixes it before the first turn: when `ox claude` starts a new session on either billing route without `--resume`/`-r`, `--continue`/`-c`, `--session-id`, `--fork-session`, `--from-pr` or `--no-session-persistence`, it adds `--session-id` with a fresh UUIDv4. Subcommands such as `mcp`, `plugin`, `update`, `doctor`, `install` and `setup-token`, the background-session commands `attach`, `kill`, `logs`, `respawn`, `rm` and `stop`, and `--version` and `--help`, are left unchanged. `desktop/tests/claude_subcommands.py` fails the Claude protocol job when a stock release lists a root command or alias that `CLAUDE_SUBCOMMANDS` in `src/clients.rs` lacks. This does not depend on a host. A resumed Claude launch names the session from `--resume <id>`. `/clear` inside Claude Code starts a new native session that the launch never sees; work after it stays covered by the launch token while the launch lives, and the launch's recorded session never changes. A session observed only after a launch has started workers (for example from an `X-Claude-Code-Session-Id` header, should a future Claude Code send one) is bound once to those workers and never replaced. A later terminal session that resumes the recorded or bound session can read and control them. Another terminal launch in the same project cannot. After the terminal exits, `ox claude --resume <id>` or `ox codex resume <id>` reclaims the workers; when no session was ever known, only the operator on the desktop or phone controls them.

Each worker carries an immutable origin stamp in the ledger and in catalog rows: relation, parent reference (project, host scope and session, or the terminal session), launch identity, whether an operator started it, runtime, route, mode, job number, requested level, granted ceiling, started preset, how the mode was decided and, for YOLO, the acceptance or grant that allowed it. A second stamp for the same session is refused. A fork of a stamped session receives the same stamp with relation `fork` and its source. A nested worker's own stamp names the worker as its parent. A handoff target carries relation `handoff` in the same stamp, so there is one lineage model.

### Permission modes for workers and handoffs

One mode model covers workers and handoff targets. Every native preset belongs to one of four ordered levels, and a child starts at its source's level, mapped to the nearest preset of the target runtime that is not more permissive:

| Level | Codex | Claude Code |
| --- | --- | --- |
| read | Read only | Plan (Default also counts as read) |
| write | Workspace | Accept edits |
| classifier | Auto-review | Auto |
| yolo | YOLO | bypass permissions |

A Codex thread that is not exactly one preset shows `Configured`, but its effective settings can still verify a ceiling: the highest level whose preset does nothing the thread could not already do without a person. Every legacy sandbox reads the whole filesystem, so it grants at least read. `untrusted` approval grants read. Granular approval grants at most write. Writing gives write when the sandbox also lets it write `/tmp` and `$TMPDIR`, and with a classifier reviewing on-request approvals it gives classifier. No sandbox gives classifier on-request and YOLO with `never`. For example, `danger-full-access` with on-request approval grants classifier, and `workspace-write` with network access or extra roots grants write. A user-defined permission profile, an external sandbox, or any field or value this build does not know grants nothing: stock Codex reports restricted reads only through the profile, never in the legacy sandbox it also sends. A preset reported by the other runtime, or no confirmed settings, also grants nothing, and the launch is refused. `desktop/ox-desk-core/src/modes.rs` holds the table, and `desktop/ox-desk-core/src/codex/access.rs` reads Codex settings. Both have tests.

- **Inherit by default, lower never raise.** `start_ox_worker` takes an optional `permission_mode`: `inherit` (the default) or a lower level, by level name or native preset name. A request above the source is refused before any process starts. `workspace_write` still works for old callers (false is read, true is write) and is capped the same way. The existing `mode` argument keeps choosing session, goal or workflow, so the permission argument has its own name. The operator's `/worker` takes `--mode <mode>`; `--write` still means write.
- **The ceiling.** For a hosted parent the ceiling is the one its live settings verify, as above. A worker or a fork of one is further capped by its own stamp, so forks, continuations and nested workers can never widen it, even if the operator later switches the worker itself to a broader mode. A terminal launch's mode cannot be verified: it may ask for read or write, inheriting gives read, and nothing above write is granted. The parent agent has no permission operation; no agent path raises its own or a child's mode.
- **Classifier modes inherit freely.** Auto-review and Claude Auto start without asking.
- **Inherited YOLO and bypass.** When a hosted agent leaves the mode at inherit, the worker starts at the verified parent’s level, including YOLO. The origin records the parent session that supplied the level. An explicit YOLO request waits for the operator unless a grant covers it. The host publishes an ask on the parent session, with the usual badge and Web Push, naming the parent, runtime, route, model and task. Its choices are Accept YOLO, Start in the highest non-YOLO mode within the ceiling (Auto-review or Auto), and Decline. `start_ox_worker` returns at once with the job number and `waiting_for_operator` (reason `yolo_acceptance`); status, list and cancel see the request, and a parent may withdraw it with `cancel_ox_worker`. The parent can never answer it: the gateway protocol has no such operation, and an agent's `yolo_confirmed` is ignored. The operator's own `/worker` or sheet starts YOLO only when the client sent its YOLO confirmation.
- **Grants.** When the operator switches a session to YOLO, both clients offer "also for its workers and handoffs". The grant is stored in the ledger with that session's scope and ID and covers every descendant: workers, their nested workers, and handoffs, through the origin chain. Revoking it, from either client, affects new spawns only; running children keep their mode and are listed with the grant. `[workers] yolo_grant_projects` in `codeox.toml` turns the grant on for every session of the listed projects; there is no global switch.
- The stamp records the started preset (`started`), how it was decided (`decided`: inherited, lowered, operator, capped) and, for a YOLO child, which acceptance or grant allowed it (`yolo`). Changing a parent's mode still requires its active workers to finish or stop first. Within a worker's ceiling the operator may change its mode on the phone or desktop. A handoff target belongs to the operator and has no stamp bound.

### Parent contract and approvals

`list_ox_workers`, `ox_worker_status`, `steer_ox_worker` and `cancel_ox_worker` keep their schemas, and `answer_ox_worker` is new. For host-owned workers the gateway forwards them to the host, which answers from the worker session's state: status, native session ID, progress and the latest assistant message as the result. The parent sees only workers it owns under the rules above. When the operator steered, continued or changed the access of a worker, its status carries an `operator` record. A host restart reports an unfinished worker as `interrupted` and never relaunches it.

Worker approvals and questions reach human clients through the normal ask path, and the parent agent may stand in for some of them. While one is pending, `ox_worker_status` reports `waiting_for_operator` with a message, the places to answer (OX Desktop and paired phones), the `ox desktop` command for the project and how many operator clients are connected, plus the open `requests`. Each request carries its `request_id`, title, detail, choices or questions, and `parent_may_answer`; when false, `operator_needed` says why. The parent answers with `answer_ox_worker` (the gateway's `answer` operation), and whichever answer arrives first decides. Policy (`parent_may_answer` in `ox-host/src/workers.rs`): questions are answers, not grants, so the parent may fill them in unless one is secret. An approval decides whether an action runs, so the parent may approve only when its own verified level (bounded by its own stamp) is classifier or YOLO, so it already acts without a person and stands in as the reviewer the way a classifier would. A choice that sets a lasting rule (a Codex exec-policy prefix, a host rule or any other amendment, whose scope the request shows in `choice_details`) stays with the operator; `parent_choices` lists the indices a parent may pick. An approval whose detail is too long to show in full also goes to the operator. A read worker's approvals always wait for a person, because approving any of them would take it beyond reading. A terminal parent's level cannot be verified, so it never approves. YOLO acceptance and every mode change stay with the operator, and the gateway still has no access operation. **Settings › Accounts › Agents › Worker requests** (`worker_approvals` in the shared Desktop preferences) set to "I answer" sends every request to a person. A Claude read worker's request to leave Plan mode is declined by the host with an instruction to reply with its findings, because its ceiling could never grant the exit. Steering is refused while a request is open. Revoking a device closes its stream but leaves the request pending for another paired device with the live token. Capability tokens and approval tokens stay in host memory.

### Operator and clients

A worker launched by a hosted agent sends its parent one short status update when it needs a person, finishes, fails, is cancelled, is interrupted, or the operator declines its launch. The host waits for the exact parent session’s next idle boundary. A closed parent receives its queued updates when reopened. The host records pending updates before sending and checks native history after an uncertain send. The latest status also appears on the parent’s Desktop and phone session rows, including after a host restart. Live device alerts are best effort. If the host stops between recording an update and broadcasting its alert, reconnecting clients still receive the parent row and the host retains its queued turn. Terminal parents can use `ox_worker_status` to read results.

An operator can start a worker attached to the selected session. On the desktop type `/worker codex:<model> [--mode <mode>] [--goal] <task>` or `/worker claude[:<model>] [--mode <mode>] [--workflow] <task>` in that session's composer. On the phone use Start worker in the session menu, which offers the same permission modes (default: inherit). The same policy applies, with the selected session as parent. Both clients nest a worker under its parent across routes through the origin stamp and keep that place after a host restart. The phone's session filter offers Active, Requests and Finished. The desktop search accepts `is:running`, `is:waiting` and `is:finished`. A YOLO acceptance is an ordinary ask on the parent session in both clients.

### Standalone fallback

With no host running, `ox claude` and `ox codex` run workers inside the launching gateway exactly as before: the gateway starts a stock app-server or `claude --print` stream, denies interactive approvals and ends its workers with the launch. The gateway cannot verify the parent's mode there, so `inherit` starts a read worker, `write` (or `workspace_write`) a write worker, and classifier or YOLO workers are refused because nothing could ask the operator. `read_ox_thread` needs the host. A host never becomes a requirement for the standalone CLI. To keep this behaviour while a host runs, set `host = "never"` in the `[workers]` table of `codeox.toml`. The default, `auto`, hands workers to a running host. A helper the host itself started always uses the host.

## Handoffs

A handoff continues a conversation in another runtime, billing route or model. The target is a new native session; the source stays as it was. A route or model change inside one runtime is a handoff too: a Claude session cannot be resumed across billing routes, because each route has its own config dir. On API routes the model is the OX alias, so choosing another alias is a route change.

**Starting one.** On the desktop type `/handoff <codex|claude>[:<alias>] [--mode <mode>] <request>` in the source session's composer, or choose "Continue in…" in the command palette, which fills that command in. On the phone use Continue in… in the session menu and choose the runtime, route and model, mode (default: inherited) and the request. Choosing YOLO in either is the confirmation that any YOLO change needs; inheriting YOLO without a grant is refused with a request to choose it explicitly. The phone sheet offers the grant with it. Before a conversation goes to a different provider than the source's, both clients say in one line which provider receives it.

**What the host does**, as one operation:

1. Validate the source. A source with a running turn, pending approvals or questions, a pending YOLO request, or another handoff starting is refused, and the refusal names what is pending.
2. Load the source's older history pages, then resolve the target route and mode under the mode model. The operator may raise as well as lower; YOLO needs the confirmation or a grant.
3. Select the carried messages (below), open the target session on its route, apply its starting preset, transfer the selection and send the new request, and stamp the target's origin with relation `handoff`. Codex receives the selection as raw Responses message items through `thread/inject_items` between `thread/start` and `turn/start`. The model sees them after Codex's own context and before the request, they survive `thread/resume`, and `thread/read` does not list them. Claude Code has no history injection, so its first user turn is one delimited, attributed `<ox-handoff>` context block followed by the request. OX never writes or edits stock session files.

The source gets a "handed off to …" mark in its row. The source's workers keep running under their original parent.

**The stamp.** The target's origin has `relation: handoff`, the source as `parent`, and a `handoff` record: source scope and session (and native ID), runtime and route, the source's mode, the resulting mode and how it was decided, and the selection as references only: carried item IDs, cut item IDs, counts, omitted ranges and the budget window. Message text is never stored in the ledger.

**Markers.** Both clients show a marker at the top of the target: source session, runtime and route, mode and why, "N messages carried, M omitted", and a link to the source. For a Codex target the marker comes from the stamp, since nothing carried appears in `thread/read`. For a Claude target the context block in the first user message is folded under the marker and only the request is shown. Clients fold only the first user message of a handoff target, once the first page of its history is loaded; any other message that starts with `<ox-handoff>` renders as typed. The source shows a link to the target, and a failed handoff's reason.

### Selection

The selection lives in `desktop/ox-desk-core/src/handoff.rs` and is deterministic and independent of the runtime.

- **Budget.** The host records the context window each stock client reports, per route and model: Claude Code's `result.modelUsage[].contextWindow` and Codex's `thread/tokenUsage/updated` `modelContextWindow`. An API handoff uses the target alias’s reported window or its OX catalog limit, taking the smaller when both are available. When the destination model is unknown, including on subscription routes, the budget starts at 64,000 tokens and shrinks to the smallest window reported on that route. 24,000 tokens are reserved for the runtime's own instructions, tools and environment, a quarter of the window (at least 8,000) for working space, and the request's own size. Sizes are estimated at one token per three bytes.
- **Always kept:** the first user request and the most recent exchange, in their original order and roles. Earlier exchanges are added newest first while they fit. An exchange is a user message and everything until the next.
- **Reduced:** commands and tools become short attributed outcomes, such as ``Command `cargo test` exited 0`` or `Files completed: src/a.rs`. Reasoning, plans, tool-call internals and attachments are dropped.
- **Cut:** an item above 4,000 tokens (or an eighth of the budget, if smaller) is cut and ends with a reference to the full item for `read_ox_thread`.
- **The request is never shortened.** If the request plus the minimum selection does not fit, or the request alone can never fit the target's context, the handoff is refused with the reason before anything starts.
- Interrupted or failed turns keep their partial text.
- **Chains never nest.** When the source is itself a handoff target (or a fork of one), the `<ox-handoff>` block in its first user message is stripped to its request. The selection records the source's own chain (`earlier`) and which item was stripped, and the note names the earlier sessions for `read_ox_thread`. A Codex source needs nothing, since injected items are not listed by `thread/read`.

A short note precedes the carried messages. It names the source, says the messages are real and not a summary, gives the counts and omitted ranges, and points at `read_ox_thread`.

### read_ox_thread

The OX MCP gateway exposes `read_ox_thread` beside the worker tools. A subscription launch has the whole gateway; an API-alias session the host runs gets a gateway with only `read_ox_thread`, so a handoff target on an API alias can read its source without gaining worker tools. The host resolves the caller by the same exact-caller rules as every parent operation (the Codex `_meta.threadId`, or the Claude helper's own session). A session may read its own handoff sources, the whole chain back through earlier handoffs, read-only and within its project. Anything else is refused: a session without a handoff source, a session outside the caller's chain, a source in another project, and terminal launches. It pages by item ID: `item` returns one item in full, `after` continues after an item, and `limit` is 1 to 100. Pages are capped at 256 KiB of item text. `desktop/tests/host_handoff_session.py` runs the real host, OX helper and stock Claude Code against a local Messages API on each release track: the target's first user turn is exactly the block and the request with a typed closing tag escaped, the model reads an omitted item in full through the gateway, and a session outside the chain is refused. If the source is not loaded, the host opens its route and history first, waiting up to 40 seconds.

### Trust model

The carried text goes only to the target runtime and its provider, never to the ledger, Web Push or logs. A handoff to another provider sends that provider real earlier messages, which the clients say before sending. Handoffs start only from a person on a paired device or the desktop. Agents can start workers, lower their mode and read their own handoff chain; they cannot start handoffs, raise any mode, answer a YOLO request, or read sessions outside their chain. Explicit YOLO requests use the operator’s acceptance or an existing grant. A hosted worker can inherit its parent’s verified YOLO level.

## Remote access and privacy

Enable Remote access in Desktop settings and use a private HTTPS Tailscale Serve origin. The HTTP listener binds to loopback. A Tailscale login header, by itself, grants no session access. Initial pairing starts from a same-user local administration socket. A paired operator may sign a request to create another short-lived invitation for their own Tailscale identity. Revoking the issuer withdraws its unredeemed invitations. The QR fragment carries a short-lived, single-use invitation. The mobile client creates a non-exportable signing key. The registration binds the device to its Tailscale identity, expected HTTPS origin, secure cookie and public key. Opening the live connection requires signing a fresh challenge. Cross-origin requests, unpaired clients, expired challenges and revoked devices are refused. Revoking a device also disconnects its live stream. Unused pairings expire after 30 days. The PWA caches its shell assets. Transcripts, invitation secrets and approval content stay out of the offline cache.

The installed iPhone web app keeps its non-exportable key in IndexedDB. WebKit gives Home Screen installations their own storage. Open the installed app and use its camera to scan a fresh same-origin invitation. QR frames are decoded on the phone with the bundled jsQR 1.4.0 decoder. No external script or camera upload is involved. [WebKit storage behavior](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/)

Settings reads and writes require the device to sign a fresh challenge bound to the request body. The host invokes the matching local OX helper with typed operations and revision checks. Key entry goes through that helper’s stdin and stays out of the session protocol. Each terminal connection additionally requires an explicit grant for this device, set through the local administration socket. A purpose-bound proof covers the operator’s requested launch. Terminal data travels on its own authenticated WebSocket and never enters the agent conversation, event replay buffer or Web Push payload. Disabling the grant or revoking the device invalidates active terminal connections. Invitations do not convey terminal access.

The phone derives input visibility from the PTY echo flag and masks unknown or no-echo input. Its Show/Hide override is local to the current prompt.

The operator reviews the host directory and program before choosing Run. The fixed sign-in commands launch the stock client. For an idle conversation, the host supplies the verified native session ID, billing route and launch arguments privately to the requesting device. The host releases that conversation when the operator chooses Run and resumes it after the terminal process exits.

The host sends encrypted Web Push directly with its VAPID identity to supported HTTPS push services. A notification contains the scoped thread identifier, a session title and an event kind. An unnamed session uses a generic label. Notifications never include message bodies, commands, tool arguments or diffs. Tapping a notification opens the corresponding session after the device reconnects.

The browser tests use a disposable TLS reverse proxy with a simulated Tailscale identity. They exercise the real browser's pairing, WebSocket authentication and revocation paths. The stock continuity fixture additionally starts Claude in the packaged desktop, closes the desktop with an approval pending, answers from paired Chromium, verifies the native command's relative file write and reopens the desktop. Testing with Oscar's phone, actual tailnet and OS notification delivery requires those devices and accounts. The manual procedure for that run is in [Remote access: real-tailnet check](tailnet-check.md).
